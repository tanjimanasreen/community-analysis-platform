# Plan 021: Prefect Milestone 3 - Theme Generation and Provider Orchestration

## 1. Goal
Design an implementation-ready architecture for introducing Prefect to the theme generation phase. This orchestrates the provider lifecycle, implements strict zero-retry defaults at the Prefect level, and establishes robust lineage for prompts and outputs without duplicating provider configuration logic or leaking live providers across orchestration boundaries.

## 2. Current-state Findings
- The core domain function is `run_theme_pipeline_from_monthly_data` inside `src/pipelines/theme_pipeline.py`.
- It dynamically builds its provider internally using `build_theme_provider` if one is not supplied.
- It processes a full batch of months natively and computes visualizations/similarity heatmaps.
- Provider fallback/routing is owned by `RoutingBenchmarkProvider` inside the factory. `CachedProvider` handles prompt-level response deduplication.
- `make test` is green. Mock and deterministic providers are available offline.

## 3. Exact Domain Function to Wrap
- **Name**: `run_theme_pipeline_from_monthly_data`
- **Signature**:
  ```python
  def run_theme_pipeline_from_monthly_data(
      monthly_data_dict: dict[str, pd.DataFrame],
      year: str,
      content_type: str,
      output_dir: str,
      config: dict | None = None,
      provider=None,
      render_visuals: bool = True,
      similarity_model_name: str = 'paraphrase-MiniLM-L6-v2',
  ):
  ```
- **Inputs**: A dictionary of loaded monthly data (topic/community matches, generated by `load_prepare_data`).
- **Outputs**: Writes `{month}_{year}_with_themes.csv`, `community_transition.csv`, and sankey/membership/similarity visual directories.
- **Returns**: `matched_df` DataFrame.
- **Provider Lifecycle**: Constructs provider once (via `config`) if `None`, applying `CachedProvider` deduplication, and reuses it for the entire batch.

## 4. Current Call Graph
- `src/cli.py` -> `run_theme_pipeline` -> `load_prepare_data` -> `run_theme_pipeline_from_monthly_data`
- `run_theme_pipeline_from_monthly_data` -> `build_theme_provider` -> `process_single_file_themes` -> `generate_llm_themes`
- Computes transitions and creates visualizations (`draw_community_transition_diagram`, `extract_themes`, `draw_theme_similarity_heatmap`, etc.).

## 5. Proposed Task Boundary
We will create a coarse Prefect task `run_monthly_themes_task` that wraps `run_theme_pipeline_from_monthly_data`.
- **Option B chosen**: The task receives serializable provider configuration and topic output references, validates them, and delegates to the domain function. The domain function locally constructs the provider once and reuses it for the complete batch.
- The task will return a `ThemeOutputBundle`. Live provider objects will never enter Prefect state.

## 6. Typed Input Contract
```python
@dataclass(frozen=True)
class ThemeInputBundle:
    monthly_topic_outputs: Mapping[str, ArtifactReference]
```
- **monthly_topic_outputs**: Mapping of month to `LDA/matched/...` CSV output generated by the Topic phase.
- The task must validate existence of these artifacts before parsing the inputs and launching the domain function.

## 7. Typed Output Contract
```python
@dataclass(frozen=True)
class ThemeOutputBundle:
    themes: tuple[ArtifactReference, ...]
    community_transitions: ArtifactReference | None
    visualizations: tuple[ArtifactReference, ...]
    provider_run_summary: ArtifactReference | None
```
No live APIs, raw prompt templates, or live API keys will cross the Prefect boundary. Small metadata about the configured primary/fallback and digest may be included.

## 8. Artifact Inventory
**Inputs:**
- `{month}_{year}.csv` from `LDA/matched/`

**Outputs:**
- `{month}_{year}_with_themes.csv`
- `community_transition.csv`
- `/sankey/...`
- `/membership_changes/...`
- `/theme_similarity/...`

## 9. Output-isolation Strategy
All outputs must be written into the `pipeline_run_id`-specific root directory, maintaining the exact schema format as previously produced. Artifact validation will rely on explicit file existence checks.

## 10. Retry Policy
- `retries=0` initially for the Prefect task.
- Fallback logic remains strictly inside `RoutingBenchmarkProvider`.
- An optional Prefect retry condition `retry_condition_fn` may be tested, but task retries will remain 0 until we have a proven transient-only error payload from the router. Exhaustion of the provider fallback chain alone is terminal.

## 11. Cache Policy
- No task-level cache initially.
- We rely on `CachedProvider` for prompt-level deduplication across duplicate keywords.
- Task caching for themes would need to include provider config, prompt version, topic keyword hashes, and output existence checks. We do not enable task-level caching yet to avoid conflict with the existing prompt-level cache.

## 12. Result-persistence Policy
- `persist_result=True` storing only `ThemeOutputBundle` references and small execution metadata in `.prefect_results/`.

## 13. Manifest and Lineage Changes
Additively extend the existing manifest to include:
- Theme stage status.
- Topic-output artifact identities.
- Provider configuration digest.
- Configured primary provider and fallback chain.
- Prompt version and generation settings digest.
- Theme output artifact references.

## 14. Flow Integration
- Extend the composition flow: `run_monthly_analysis_flow` -> network -> topics -> themes.
- If executed in isolation, `run_theme_analysis_flow` or a dedicated entry block takes an explicitly validated `ThemeInputBundle` and executes the theme task.

## 15. Optional-stage Dependency Rules
- **Themes only**: Caller supplies a validated `ThemeInputBundle` constructed from prior topic outputs.
- **Run with no topic outputs**: Must fail immediately before provider construction is triggered.
- **Run Topics + Themes**: Piped outputs directly feed the Theme inputs from the current pipeline run.

## 17. Tests
- **Provider lifecycle**: Assert `build_theme_provider` is called exactly once per task inside the domain wrapper. Assert no live provider leaked to Prefect state.
- **Routing**: Validate the task succeeds using the MockProvider configurations without any live HTTP calls.
- **Inputs and outputs**: Missing theme inputs fail early. Output hashes are accurately captured and validated.
- **Configuration lineage**: Changes to prompt/provider mutate the configuration digest predictably.
- **Flow tests**: Test with `prefect_test_harness()` using MockProvider and isolated temporary directories.

## 18. Manual Smoke Test
- Run `run_monthly_analysis_flow(themes_only=True)` with a temporary `PREFECT_HOME`, isolated output dir, mock provider (`LLM_PROVIDER=mock`), and tiny topic-output fixtures. Verify generated themes CSV and ensure zero external HTTP calls occur.

## 19. Acceptance Criteria
- Exact current theme-domain function is wrapped.
- Provider ownership is unambiguous (constructed once locally in the domain).
- Live provider objects never cross task boundaries.
- Provider fallback remains router-owned.
- Theme task retries remain zero initially.
- Mock-provider tests cover primary and fallback behavior.
- Theme outputs are typed artifact references.
- Manifest records provider and prompt lineage.
- No live external API is used in tests.
- Full `make test` passes.
- Fresh isolated mock smoke test passes.
- MLflow is not added in this milestone.
- Working tree is clean after a focused commit.

## 20. Risks
- **Risk**: Overlapping caching systems (task vs prompt level).
  - **Mitigation**: Disable Prefect task caching for themes initially.
- **Risk**: Creating new providers per community or month.
  - **Mitigation**: The design injects config to `run_theme_pipeline_from_monthly_data` which handles provider construction correctly before looping.

## 21. Rollback Strategy
- Remove `src/orchestration/tasks/theme_tasks.py`. The legacy execution continues unchanged.
